## Установленный lifecycle

Серверный bootstrap загружает ModuleScripts из Services, сортирует по Order, выполняет Init всех сервисов, затем Start всех сервисов. В исходной основе два сервиса: NetworkService (Order 10) и TagService (Order 20); её старт 2 services / 0 controllers подтверждён пользователем. Первый игровой этап добавляет RoundService (Order 30) и RoundController. При следующем Test ожидаются 3 services / 1 controllers; это ещё не проверено в Studio.

GameConfig содержит DEV/debug, идентификатор и название игры, local solo PC и CoreLoop. Баланс хранится в `src/shared/Game/Balance.luau`; он соответствует стартовым значениям GD spec. Длительность 420–600 секунд — ориентир; игровое правило тайм-аута не вводится. Persistence.Enabled остаётся false, модули player-data/economy отсутствуют.

Будущие игровые реализации располагаются в `src/server/Game` и `src/client/Game`; подключающие сервисы и контроллеры — в Services/Controllers, которые уже читает bootstrap. Не помещать игру в Logger, NetworkService или TagService.

## Серверное состояние и границы доверия

Сервер принимает окончательное решение по `ready/active/escaped/caught/aborted`, выбранному слоту и владельцу ключа, состоянию ворот, поимкам, защите после возврата, спринту, единичной награде и балансу. Клиенту нельзя передать собственное количество алмазов, индекс скрытого ключа, число оставшихся попыток или команду «победа».

Проверки будущих запросов: тип/форма, принадлежность к текущему игроку/раунду, разрешённое состояние, частота, ресурс, доступность и дистанция до объекта, отсутствие твёрдой преграды. При конфликте захват имеет приоритет, как в GD spec. Никакой доступной клиенту команды начисления награды не планируется.

Shared config доступен клиенту, но изменение его локальной копии не меняет серверный результат. Серверный баланс хранится в памяти текущего теста и прекращает существование вместе с ним.

## Tags + Attributes: планируемый контракт

**Постоянной сцене tags не назначались.** Временный прототип назначает теги своим старту, слотам, воротам, выходу, бочкам и зоне поля. Теги монстра/патруля остаются планом будущего этапа.

| Tag | Объект | Attributes | Проверка |
|---|---|---|---|
| corn_spawn | SpawnLocation или якорный BasePart | spawn_id: string | Для solo выбран один доступный старт |
| corn_key_slot | Якорный BasePart/Attachment | slot_id: string | Уникальный id, доступность по земле и около 15 слотов |
| corn_gate | Model ворот с определённым проходом | gate_id: string | Одни ворота, закрытое и открытое состояния |
| corn_exit | Объём выхода за воротами | gate_id: string | Совпадает с воротами, закрытые ворота не дают победу |
| corn_scarecrow | Model монстра | monster_id: string | Один монстр; центр исходного появления |
| corn_patrol_point | Якорный BasePart/Attachment | patrol_order: number | Достижимые точки маршрута |
| corn_barrel | Model/BasePart бочки | Без обязательных attributes | Доступна для обзора, не исключает захват |
| corn_field_zone | Объём зоны кукурузы | Без обязательных attributes | Связывает шелест с нахождением в поле |

Tags не назначаются каждому растению: одна зона и подготовленные ключевые объекты достаточны для первого MVP. Игровая система создаёт/перемещает единственный ключ на старте, при подборе и падении. Автор сцены не должен вручную создавать много независимых скриптов или дублирующихся ключей.

## Будущие network endpoints

В EndpointNames зарегистрированы request_round_action и round_snapshot для первого этапа; точный действующий протокол описан ниже. request_sprint и расширенный snapshot с попытками/выносливостью остаются планом следующего этапа:

| Endpoint | Направление | Контракт | Серверная проверка |
|---|---|---|---|
| request_round_action | Client → Server | action: start/retry/abort | Перечисление, текущий исход, один раунд, limit 2 запроса/с |
| request_sprint | Client → Server | enabled: boolean | Активный игрок, допустимое состояние, запас; limit 10 переключений/с |
| round_snapshot | Server → Client | Цель, исход, попытки, выносливость, наличие ключа, награда/баланс | Формируется сервером; без скрытого слота и координат ключа |

Для ключа/ворот использовать близкое взаимодействие с серверной проверкой; точный адаптер E/ProximityPrompt определить в первом slice после чтения сцены. RemoteEvent переносит намерение, а принимающий сервис определяет результат. [Roblox: remote events](https://create.roblox.com/docs/scripting/events/remote).

NetworkService — реестр объектов связи, а не готовая защита или сеть опубликованного мультиплеера. Отдельные рейтинги, партии, платежи и cloud profiles сюда не добавлять.

## Сброс и очистка будущего раунда

Новый раунд: ключ создаётся в одном выбранном слоте; ворота закрыты; монстр в центре и до 15 секунд неактивен; поимки 0; две попытки; запас спринта полный; старые переходы и подписки отменены. Временный баланс теста сохраняется.

Первая поимка: ключ падает около захвата, игрок возвращается на старт, монстр по предложенному дизайну возвращается в центр, защита 5 секунд; старый таймер охоты не перезапускается. Уже открытые ворота сохраняются. Вторая поимка — окончательный исход. После исхода повторные сигналы не меняют награду.

TagService.Destroy отключает все его подписки. Перед игровыми раундами решить срок жизни подписок: world bindings живут весь тест, а действия и callbacks конкретного раунда отключаются отдельно. Не вызывать глобальный Destroy одного singleton-сервиса из случайного игрового объекта.

## Первый игровой этап: временный прототип цикла

Статус: код реализован, StyLua/Selene/Rojo build и sourcemap пройдены; Test игровых механик ещё не выполнен. Запуск основы подтверждён пользовательским скриншотом 2026-10-09_13-48-32.png: ServerBootstrap Started 2 services, ClientBootstrap Started 0 controllers; ошибок основы в видимом Output нет. Сообщения стороннего плагина и Disconnect при остановке теста не относятся к ошибкам основы.

Сцена пока содержит Baseplate/SpawnLocation. Для проверки ключевого цикла сервер в режиме DEV и solo_local создаёт только свою временную Model CornPrototypeRuntime в Workspace: поднятая площадка, старт, 15 слотов, три бочки из Parts, закрытые ворота и зона выхода. Исходные Baseplate/SpawnLocation/Terrain/Lighting и .rbxl не изменяются. Остановка Test удаляет runtime-сцену средствами Studio. Размеры этой площадки — технический стенд; размеры будущего ручного кукурузного поля остаются TBD. Кукуруза подключается отдельным шаблоном автора; охота, попытки и спринт в этот этап не входят.

RoundService подключает Game/SoloRound; NetworkService по-прежнему только реестр remotes. Game/GreyboxWorld владеет исключительно созданной им Model. RoundController и Game/RoundHud отвечают за меню, цель, результат и отправку намерений. Временный баланс хранится в SoloRound до остановки Test.

Точные endpoints этого этапа:

| Endpoint | Направление | Payload |
|---|---|---|
| request_round_action | Client → Server | Одна строка: sync / start / retry / abort / menu; token bucket capacity 2, refill 2/с |
| round_snapshot | Server → Client | phase, has_key, gate_open, session_diamonds, reward_diamonds, elapsed_sec, notice (ключ локализации или пустая строка) |

Snapshot не содержит выбранный слот или координаты ключа. phase: ready / preparing / active / escaped / aborted. sync нужен после подключения клиентского обработчика, чтобы не потерять начальный snapshot. start допустим в ready, retry — после исхода, abort — в active/preparing, menu — после исхода; завершённый раунд не начисляет награду повторно. Отдельной команды выдачи алмазов нет.

Взаимодействие — ProximityPrompt с клавишей E и серверной проверкой владельца/состояния, текущего живого персонажа, Enabled, дистанции 4 studs, луча без твёрдой преграды; для ворот дополнительно передняя сторона. Открытие ворот расходует ключ; победа наступает только при входе живого игрока в зону за открытыми воротами. Высокие сплошные границы исключают обход закрытых ворот в обычном управлении.

Повтор уничтожает только временный ключ, закрывает ворота, выбирает один новый слот, возвращает игрока на старт; баланс сохраняется. Reset/смерть персонажа прерывают незавершённый раунд без награды. Новый персонаж в меню возвращается на временный старт. Подготовка имеет ограниченное ожидание персонажа и проверяет актуальность поколения раунда после ожиданий; abort/уход игрока отменяют старую подготовку. Владельцем одного runtime-раунда может быть только один игрок.

### Ассет кукурузы для временной площадки

Автор предоставил FBX и PNG. Точные копии и отдельный FBX с привязкой PNG подготовлены в assets/corn; проверка geometry/UV описана в asset-verification.json. Импорт в Studio ещё не выполнен. Пользователь импортирует *_textured.fbx и сохраняет Model или MeshPart в ServerStorage/CornPlantTemplate. Эту область Rojo не синхронизирует; источник пользовательского ассета сохраняется в Studio.

Game/CornField клонирует только этот шаблон в собственную runtime-площадку, не меняя оригинал. Все части клона Anchored=true, CanCollide/CanTouch/CanQuery=false, CastShadow=false; листва не мешает движению и близкому E-взаимодействию. Предварительные технические значения стенда: высота 8 studs, шаг 4.5 studs, около 500 растений, 15 просветов вокруг слотов. Это не утверждённые размеры финального поля. Без шаблона ключевой цикл работает на пустой площадке и пишет понятное предупреждение в Output; проверка кукурузного поля остаётся открытой.
